# Миграция проектов на .NET 10

Переводи проект на `net10.0` только после определения его типа и требований
потребителей. Для приложений обычно меняют TFM на `net10.0`; для библиотек
совместимость с .NET Framework, Unity и другими платформами может требовать
сохранения `netstandard` или multi-targeting. Не считай замену строки TFM
завершённой миграцией.

## 1. Инвентаризируй решение и зафиксируй исходное состояние

1. Проверь `git status`; не перезаписывай и не откатывай существующие изменения.
   Не создавай commit/push без прямой просьбы.
2. Найди все проекты решения, включая тесты, инструменты, shared projects и
   проекты, которые подключаются через `ProjectReference`. Сверь значения
   `TargetFramework`/`TargetFrameworks` и условия в проектах, `Directory.Build.*`,
   `Directory.Packages.props`, `global.json`, `NuGet.config` и lock-файлах.
3. Определи, какие проекты являются запускаемыми приложениями, тестами,
   библиотеками или NuGet-пакетами. Для библиотек выясни реальные целевые
   платформы потребителей и обязательные контракты поддержки; не угадывай их по
   одному текущему TFM.
4. Проверь используемые SDK и runtime (`dotnet --info`, `dotnet --list-sdks`),
   способ публикации и развёртывания, CI, Docker/контейнерные образы, скрипты,
   IDE/workloads, нативные зависимости, архитектуры и операционные системы.
5. Запусти доступные исходные restore/build/test и запиши существующие ошибки,
   предупреждения и неподдерживаемые проверки. Не приписывай миграции проблемы,
   которые были до неё.

Если инструменты доступны, сначала можно выполнить оценку через GitHub Copilot
upgrade. Это необязательный помощник, не источник истины: проверяй его план,
изменения и совместимость по проекту и актуальным официальным руководствам.
Не требуй установки агента, расширения или платных инструментов ради миграции.

## 2. Выбери целевой TFM

### Приложения на .NET 5 или .NET 8

Для приложения, которое должно работать на .NET 10, целевой TFM — `net10.0`.
Для специальных приложений используй правильный TFM и workload по документации
соответствующего стека (например, Windows-specific TFM для desktop, либо
поддерживаемый TFM/модель для MAUI и Azure Functions). Не переводить проекты
`net5.0`/`net8.0` механически в `net10.0`, если тип приложения требует иного.

Переход с .NET 5 или 8 можно выполнять напрямую: не вводи промежуточные целевые
версии автоматически. Изучи релевантные breaking changes для исходной версии и
каждой последующей major-версии до 10, а также руководства конкретных стеков и
пакетов. Промежуточный шаг допустим только при конкретном подтверждённом
ограничении, с объяснением причины.

### Библиотеки на .NET Standard

У .NET Standard нет версии 10; не создавай TFM наподобие `netstandard10.0`.
Начиная с .NET 5, .NET Standard в большинстве новых сценариев не нужен, но
изменение TFM библиотеки — это изменение её контракта для потребителей, а не
простое техническое обновление.

| Требования потребителей | Подход |
| --- | --- |
| Только приложения на .NET 10 и новее; ограничение старых платформ приемлемо | Перевести библиотеку на `net10.0`. |
| Одновременно .NET 10 и .NET Framework либо платформы, которым нужен общий API-контракт | Рассмотреть `net10.0;netstandard2.0`. Убедиться, что зависимости поддерживают оба TFM. |
| Потребители уже используют `netstandard2.0`, и их нельзя обновить | Сохранить `netstandard2.0`; при необходимости добавить `net10.0` как дополнительный target. |
| Текущий TFM `netstandard1.x` или `netstandard2.1` | Не заменять наугад. Составить список потребителей и проверить совместимость API и пакетов. Переход на `netstandard2.0` может исключить платформы, которые поддерживали только старый 1.x; `netstandard2.1` не поддерживается .NET Framework. |
| Неизвестны версии/платформы потребителей опубликованного пакета | Считать совместимость обязательной до подтверждения обратного; не удалять старые TFM в рамках молчаливого обновления. |

`netstandard2.0` поддерживается .NET Framework 4.6.1+, но при возможности
потребления из .NET Framework учитывай рекомендации Microsoft по более новым
целям .NET Framework и проверь проект на реальных целевых runtime. Совместимость
TFM при восстановлении пакетов сама по себе не доказывает runtime-совместимость.
Если библиотеке нужны платформенные API, выбирай multi-targeting и аккуратное
ветвление по TFM вместо потери общего target. Меняй контракт пакета только с
явным указанием затронутых потребителей и последствий.

## 3. Составь план изменений по всему контуру

До правок перечисли поверхности, которые нужно обновить:

- TFM всех согласованных проектов, включая тесты и внутренние инструменты;
- установленный .NET 10 SDK и `global.json`, если SDK закреплён;
- NuGet-пакеты и централизованное управление версиями;
- CI runners/images, Dockerfile, базовые build/runtime images, release и deploy
  конфигурацию;
- локальные скрипты, launch profiles, документацию и проверки, где зашиты старые
  версии SDK/runtime;
- workloads, RID, архитектуры и специфичные настройки publish/trim/AOT, если они
  используются.

Меняй только необходимые версии. Обновляй согласованные `Microsoft.AspNetCore.*`,
`Microsoft.Extensions.*`, EF Core и другие пакеты согласно их поддержке .NET 10
и собственным правилам версионирования. Не повышай автоматически все сторонние
зависимости до latest. Проверь package source, lock files, транзитивные
зависимости, устаревшие/заменённые пакеты и совместимость каждого важного
провайдера или генератора кода. Сохраняй закрепление SDK и версий пакетов, если
оно применяется в проекте.

## 4. Выполни миграцию итеративно

1. Обнови выбранные TFM и необходимые настройки SDK/workload.
2. Выполни restore и сборку. Исправляй ошибки компиляции по существу; для новых
   предупреждений разберись, относится ли оно к реальной проблеме. Не глуши
   пачкой analyzers, nullable, warnings-as-errors или несовместимые API.
3. Прочитай breaking changes для `.NET 6`, `.NET 7`, `.NET 8`, `.NET 9` и
   `.NET 10` в тех областях, которые реально использует проект. Для ASP.NET Core,
   EF Core, MAUI, desktop, Azure Functions, контейнеров, SDK/MSBuild и внешних
   пакетов изучи их отдельные migration/breaking-changes руководства и путь от
   установленной версии.
4. Проверь изменения поведения и конфигурации, не ограничиваясь компиляцией:
   сериализация и nullability, HTTP/TLS/networking, DI/hosting, логирование,
   обработка сигналов, файловая система/криптография, globalization, trimming,
   single-file/AOT, контейнерные образы и publish defaults — только там, где это
   применимо проекту.
5. Для EF Core обнови согласованно runtime/provider/tools, проверь миграции и
   сгенерированный SQL. Не выполняй миграции или destructive-команды против
   production. Для multi-targeted проектов укажи `--framework` в командах `dotnet
   ef`, если этого требует используемая версия инструмента.
6. После каждого логического блока повторяй узкие build/tests; не смешивай
   несвязанный рефакторинг, замену библиотек или архитектурную модернизацию с
   обязательными для .NET 10 исправлениями.

## 5. Проверь результат на целевых сценариях

Выполни команды, соответствующие репозиторию; если проект использует solution,
соблюдай его обычный способ запуска проверок:

```sh
dotnet --info
dotnet restore <solution-or-project>
dotnet build <solution-or-project> --no-restore
dotnet test <solution-or-project> --no-build
```

Для библиотек проверь сборку **каждого** TFM и, когда пакет публикуется,
содержимое `.nupkg` и выбор правильного asset в sample/test потребителях:
старейший обязательный target и `net10.0`. Проверь API/поведенческую
совместимость публичного API, если пакет уже используется извне.

Для приложений проверь предусмотренные проектом интеграционные/e2e тесты,
`dotnet publish` с фактическими RID/настройками и контейнерную сборку, если она
используется. Проверь запуск опубликованного артефакта на целевом .NET 10 runtime,
конфигурацию окружения, health checks и критичные пользовательские сценарии.
Проверяй все затронутые CI/deploy-этапы; локальный build не доказывает, что
производственный образ или runtime обновлены.

Не делай вывод «миграция завершена», если не проверены обязательные targets,
тесты, публикация или потребители. Если окружение, workload, секрет или внешний
сервис недоступны, назови конкретно непроверенную часть и не выдавай её за
успешную.

## Завершение

Сообщи кратко:

- какие проекты и TFM изменены;
- для библиотек — почему выбран `net10.0`, сохранён `netstandard` или применён
  multi-targeting, а также какие потребители остаются поддержанными;
- существенные изменения API/поведения, зависимостей, CI/deploy и настройки SDK;
- точные команды проверок и их результаты;
- непроверенные сценарии и риски совместимости.

Не создавай commit/push и не выполняй production deployment без прямой просьбы.
