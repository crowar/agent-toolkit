# fix-ci-failures

Находит причину падения сборки и исправляет код. Скрипты — Python 3 (только stdlib), лежат в `scripts/`.

## 0. `.env`

Ключи имеют уникальный префикс `CIFIX_`, чтобы не конфликтовать с другими настройками проекта:

```
CIFIX_GITLAB_URL=    CIFIX_GITLAB_TOKEN=   (токен: scope api)
CIFIX_SONAR_URL=     CIFIX_SONAR_TOKEN=
```

Любой скрипт: если `<корень репо>/.env` нет — создаёт его; если он уже есть — **дописывает в конец только недостающие** `CIFIX_*` ключи (остальное содержимое не трогает). Также добавляет `.env` в `.gitignore`. Если обязательные значения пусты — завершается с кодом 2: попросите пользователя заполнить `.env` (не просите токены в чат, не печатайте и не коммитьте их) и повторите. Переменные окружения с теми же именами имеют приоритет над файлом.

## Сценарий 1: по локальной ветке

1. `python <skill>/scripts/gitlab_mr.py` (опции: `--branch`, `--mr IID`, `--tail N`). Скрипт берёт проект из `origin`, ищет MR ветки, берёт последний pipeline и для каждой упавшей job выводит ключевые строки и хвост лога. Найденные Sonar-ссылки печатаются в `SONAR_LINKS`.
2. Классифицируйте упавшие jobs:
   - **Unit-тесты**: найдите упавший тест в логе, воспроизведите локально той же командой, что в job (см. `.gitlab-ci.yml`), исправьте код (или тест, если он устарел — объясните почему), перезапустите.
   - **Sonar** (`ERROR: QUALITY GATE STATUS: FAILED - View details on <url>`): перейдите к сценарию 2 с этой ссылкой.
   - **Загрузка зависимостей / Nexus** (`go mod download`, `403 Forbidden`, `REQUESTED ITEM IS QUARANTINED`): перейдите к сценарию 4.
   - **Прочее** (компиляция, lint, зависимости): исправьте по тексту ошибки.

## Сценарий 2: прямая ссылка на Sonar

`python <skill>/scripts/sonar_issues.py "<url>"` — url вида `https://sonar/dashboard?id=KEY&pullRequest=154` (или `&branch=`). Выводит статус Quality Gate с нарушенными условиями, нерешённые issues (severity, файл:строка, правило, сообщение), security hotspots и метрики нового кода.

Исправление:
- Issues/hotspots: откройте файл по `файл:строка`, исправьте причину по сути правила, а не подавлением (`@SuppressWarnings`, `// NOSONAR` — только с обоснованием и согласием пользователя).
- Падение по покрытию/дубликатам на новом коде: добавьте тесты на непокрытые строки / уберите дублирование.
- Правило непонятно: `/api/rules/show?key=<rule>` через `sonar_get` из `scripts/common.py`.

## Сценарий 3: замечания code review в GitLab MR

1. Получите незакрытые review threads: `python <skill>/scripts/review_comments.py --mr IID`.
   Для каждого замечания изучите контекст кода и ветки, проверьте, действительно ли оно
   корректно, применимо и ещё не исправлено. Не считайте замечание валидным только
   потому, что его оставил reviewer.
2. Валидные замечания исправьте в коде; нерелевантные/ошибочные не исправляйте вслепую —
   объясните пользователю причину и оставьте обсуждение открытым.
3. Запустите подходящие тесты/проверки. Только после успешного исправления и проверки
   ответьте в тот же thread и разрешите его:

   `python <skill>/scripts/review_comments.py --mr IID --reply DISCUSSION_ID --message "Исправлено: <кратко что изменено>. Проверки: <команды и результат>."`

   Скрипт сначала публикует ответ, затем вызывает GitLab API для resolve. Если ответ
   прошёл, а resolve завершился ошибкой, сообщите об этом явно: thread останется открытым.
   Не отмечайте незакрытыми или непроверенными исправлениями.

## Сценарий 4: зависимость в карантине Nexus / Sonatype IQ

Работайте через HTTP/API (`curl` или Python stdlib) и CLI менеджера зависимостей.
Не используйте Playwright, MCP Playwright или другую браузерную автоматизацию.

1. **Получите исходную ошибку.** Если дана ссылка GitLab `/<project>/-/jobs/<job_id>`,
   получите именно её trace через `GET /projects/:url_encoded_project/jobs/:job_id/trace`
   с помощью `gitlab_get(..., raw=True)` из `scripts/common.py` (trace — текст,
   не JSON), не подменяйте job последним pipeline.
   Авторизация — только на настроенный `CIFIX_GITLAB_URL`.
   Из лога сохраните команду, модуль, версию и полный URL нескачавшегося артефакта.
2. **Подтвердите карантин.** Повторите GET именно этого URL и изучите HTTP-статус
   и тело ошибки (например, `curl --silent --show-error --max-time 60 --include "$ARTIFACT_URL"`).
   Обычный `403` ещё не означает карантин: без маркера
   `REQUESTED ITEM IS QUARANTINED` проверяйте права, авторизацию и настройки proxy.
   При наличии маркера извлеките актуальную ссылку IQ из ответа. Не используйте
   старый идентификатор отчёта из примера: ссылки могут меняться и истекать.
3. **Установите причину и кандидатов через IQ.** Проверьте, что ссылка ведёт
   на доверенный пользователем HTTPS-хост IQ. Для ссылки вида
   `/ui/links/repositories/quarantinedComponent/<id>` запрашивайте на том же origin:

   ```text
   GET /rest/repositories/quarantinedComponent/<id>/overview
   GET /rest/repositories/quarantinedComponent/<id>/policyViolations
   GET /rest/repositories/quarantinedComponent/<id>/remediation
   GET /rest/repositories/quarantinedComponent/<id>/otherVersions?page=1&pageSize=5&asc=false
   ```

   Это внутренние маршруты UI IQ, они могут меняться между версиями сервера.
   Проверяйте статус и формат ответа, разбирайте JSON структурным парсером;
   HTML оболочки SPA или формы входа не является отчётом.
   Сверьте координаты компонента и версию; зафиксируйте нарушенные политики,
   CVE / severity (если есть), рекомендации и разрешённые версии. При необходимости
   получите остальные страницы `otherVersions` по метаданным пагинации.
   При истечении ссылки повторите GET артефакта. Если API недоступен, требует входа
   или изменился, запросите у пользователя экспорт отчёта / сведения о политиках
   и разрешённых версиях. Не придумывайте причины и не переходите к браузеру.
4. **Проверьте кандидата в том же Nexus, что использует CI.** Для Go используйте
   URL из ошибки, а не угадывайте репозиторий по названию в IQ. Список версий:
   `<proxy>/<module>/@v/list`; сведения и файлы кандидата:
   `<proxy>/<module>/@v/<version>.info`, `.mod`, `.zip`.
   Для пути модуля и версии соблюдайте Go proxy escaping (например, `A` → `!a`).
   Список `@v/list` — строки версий, даже если сервер прислал Content-Type JSON;
   он может быть неполным или устаревшим. Наличие версии в списке или UI Nexus
   не доказывает разрешение загрузки. Нужен успешный GET файлов, включая ZIP,
   без ответа карантина; один HEAD недостаточен. Проверяйте содержимое, чтобы
   не принять HTML входа с HTTP 200 за артефакт.
5. **Проверьте совместимость до изменения.** Выбирайте разрешённую стабильную
   версию с минимальным необходимым изменением, учитывая рекомендацию IQ.
   Сопоставьте `go` / `toolchain` кандидата с `go.mod`, `go.work`, версией Go и
   образом CI; проверьте breaking changes, `replace`, источник транзитивной
   зависимости (`go mod graph`, `go mod why -m <module>`) и связанные модули.
   Для OpenTelemetry API, SDK, metric, trace и exporters учитывайте их реальные
   требования: не присваивайте всем модулям один номер механически.
   Не повышайте Go или образ CI без согласования; если совместимых разрешённых
   версий нет, сообщите блокер и варианты пользователю.
6. **Обновите и воспроизведите сборку.** В целевом модуле выполните
   `go get <module>@<allowed-version>` и `go mod tidy` с теми же настройками
   корпоративного proxy, что в CI. Проверьте изменения `go.mod` и `go.sum`,
   включая транзитивные обновления; не редактируйте checksum вручную и не
   удаляйте lock-файлы. Сначала проверьте реальную загрузку кандидата через
   `go mod download -json <module>@<allowed-version>` с отдельным временным
   `GOMODCACHE`, чтобы локальный кеш не скрыл блокировку, затем повторите
   упавшую команду `go mod download`, `go mod verify` и проверки затронутого
   модуля / команду сборки из job. Проверяйте код возврата и поле `Error` JSON.
   Не меняйте глобальные настройки Go; временный кеш удалите после проверки.
   Новую блокировку транзитивной зависимости разбирайте по тому же сценарию.

Пример: `go.opentelemetry.io/otel/sdk@v1.38.0` возвращал карантин с политикой
`Security-High` из-за `CVE-2026-24051` и `CVE-2026-39883` (CVSS 7.0).
IQ рекомендовал `v1.47.0` без нарушений; GET её `.info`, `.mod`, `.zip` через
тот же proxy проходил. Однако `.mod` требует Go `1.26.0`: доступность не равна
совместимости. Это пример диагностики, а не закреплённая разрешённая версия;
при каждом запуске проверяйте текущие политики, доступность и toolchain проекта.

## Завершение

- Запустите локально тесты/линтер затронутого модуля.
- Кратко отчитайтесь: что упало, причина, что изменено, что не удалось проверить локально (Sonar-скан пересчитается только после push).
- Для карантина укажите модуль, старую и выбранную версии, политику / CVE,
  источник разрешения (IQ и проверка Nexus), совместимость Go и результаты загрузки / тестов.
- Не делайте commit/push без просьбы пользователя.

## Ограничения

- Токены используются только для запросов к `CIFIX_GITLAB_URL` и `CIFIX_SONAR_URL`.
- Не передавайте эти токены Nexus / IQ или по редиректам на другие хосты.
   Если Nexus / IQ требует отдельные секреты, используйте только согласованные
   `CIFIX_NEXUS_*` / `CIFIX_IQ_*` ключи в `.env` целевого репозитория; не просите их в чат.
- Не обходите карантин: не переключайтесь на публичный proxy / `direct`, не добавляйте
   fallback в `GOPROXY`, не меняйте `GONOPROXY` / `GOPRIVATE` ради обхода, не отключайте
   checksum / TLS и не снимайте политики или карантин. Нужна разрешённая совместимая
   версия либо согласованное решение владельца политики, а не обход защиты.
- Скрипты по умолчанию читают данные. `review_comments.py` изменяет MR только при явном
  запуске с `--reply` и `--message`; для ответа и resolve токену GitLab нужен scope `api`.
- Лог job может быть большим — скрипт обрезает вывод; при необходимости читайте полный trace: `GET /projects/:id/jobs/:job_id/trace`.
